# Sakura 个人数据与博客管理路线图

更新日期：2026-07-23
当前状态：仅规划，尚未开始实现

## 1. 项目目标

把 Sakura 桌宠作为个人工作的统一入口，第一阶段负责：

- 记录、查询和提醒学习及工作任务；
- 用文字气泡和语音播报今日任务与提醒；
- 自动生成每周工作总结，经确认后保存到私有 GitHub 仓库；
- 创建和管理 Astro 博客的 Markdown 草稿，经确认后发布；
- 在发布博客后自动完成构建、部署和结果通知。

复杂任务规划、无人确认的公开发布，以及让 Codex 或 Claude Code 长期驻留运行，不属于第一阶段。

## 2. 已确认的通用原则

- Sakura 支持 Windows 开机自启动。
- 文本气泡是完整、权威的信息来源，语音只播报摘要。
- 输入采用混合确认模式：
  - 日期、时间和动作明确时可直接保存并回显；
  - 表述含糊、信息冲突、批量修改或危险操作时必须确认。
- 简单任务管理由 Sakura 本身完成，不要求 Codex 或 Claude Code 一直开启。
- 所有公开发布和外部上传都设置明确的用户确认门。
- 密码、Token、SSH 私钥和 QQ 邮箱授权码不得保存到 Git 仓库。

## 3. 任务与提醒

### 3.1 今日任务

当用户询问“今天有什么工作”时，Sakura 按以下顺序回答：

1. 已逾期但尚未完成的任务；
2. 计划今天处理的任务；
3. 截止日期为今天的任务。

重复任务需要合并展示，文字气泡显示完整列表，语音播报数量、逾期项和最重要事项。

### 3.2 主动提醒

- 明确设置提醒时间的任务由 Sakura 主动弹出气泡并进行语音播报。
- 如果关机期间错过提醒，Sakura 下次启动时补充提醒。
- 第一版接入 Windows 任务计划程序和 QQ 邮箱 SMTP，作为 Sakura 未运行时的补充提醒。
- 设置了截止时间但没有单独指定提醒规则时，默认发送两封邮件：
  - 截止时间前 24 小时；
  - 截止时间前 2 小时。
- 默认不在截止时再发送第三封邮件；用户可以在录入任务时明确指定其他提醒时间。
- Sakura 将邮件提醒写入本地 SQLite 队列，记录计划发送时间、状态、发送时间、重试次数和错误信息。
- 当前设备是笔记本电脑，第一版采用省电模式。
- Windows 任务计划程序在电脑清醒时每 10 分钟运行一次独立提醒程序，同时在用户登录或从睡眠中恢复后尽快补检查。
- 计划任务允许在电池供电时短暂运行，但禁止为了发送提醒主动唤醒睡眠中的电脑。
- 提醒程序只处理已经到期但尚未成功发送的记录，不启动 Sakura 窗口，也不调用 Codex、Claude Code或其他大模型。
- QQ 邮箱使用 SMTP 授权码，不使用邮箱登录密码；授权码保存在 Windows 凭据管理器中，不写入数据库、配置文件或 Git。
- 发送失败时保留提醒并稍后重试；已经成功发送的提醒不得重复发送。
- 电脑关机期间无法按时发送，本地方案在下次开机后补发，并在邮件中注明这是错过时间后的补充提醒。

### 3.3 简单重复提醒

- 第一版支持按星期重复的简单提醒，并允许暂停、恢复、修改时间和删除整个重复提醒。
- 当前股票提醒规则为：每周一至周五 14:00，提醒用户检查股票买卖计划。
- 提醒渠道沿用主动提醒设置：Sakura 运行时使用文字气泡和语音，邮件由独立提醒程序发送。
- 该提醒只提示用户检查自己的计划，不分析股票、不生成买卖建议，也不连接或操作证券账户。
- 简单重复提醒允许延迟最多 30 分钟；例如 14:00 的股票提醒可以在 14:30 之前补发。
- 如果提醒程序在计划时间超过 30 分钟后才恢复运行，则将本次记录标记为“已过期跳过”，不再发送邮件、气泡或语音，但不影响下一个重复周期。
- 截止任务的补发规则不受这项 30 分钟限制影响。
- 周一至周五模式不会自动识别法定节假日和证券市场休市日。
- “实际交易日模式”作为后续备选方案写入路线图，不进入第一版；启用前需要确定可靠的交易日历来源、更新方式和离线回退规则。

### 3.4 后续可选的服务器提醒模式

- 服务器提醒模式已纳入后续路线图，但不进入第一版实施。
- 选择服务器模式后，笔记本关机或睡眠时，服务器仍可以在截止前 24 小时和截止前 2 小时准时发送 QQ 邮件。
- 本地 Sakura 只向服务器同步发送提醒所必需的最少信息，不同步完整聊天记录和无关个人数据。
- 服务器端需要独立的提醒队列、身份认证、加密传输、QQ 邮箱授权码保管、失败重试和发送审计。
- 切换到服务器模式前，需要单独确认服务器运行环境、接口安全、数据保留周期和离线修改冲突处理。
- 第一版仍以本地 SQLite、Windows 任务计划程序和省电模式为准。

### 3.5 数据保留

- 未完成任务一直保留，直到完成或取消。
- 已完成和已取消任务的原始记录保留 14 天，之后自动清理。
- 原始任务数据只保存在本地 SQLite 数据库中，不提交 GitHub。

## 4. 每周总结与私有备份

- 每周日 20:00（Asia/Shanghai）自动生成本周总结草稿。
- 如果当时电脑或 Sakura 未运行，下次启动时补生成。
- 总结由本地任务数据计算事实，再由 Sakura 当前使用的模型整理成自然语言。
- 模型不可用时使用固定模板生成，不依赖 Codex 或 Claude Code。
- Sakura 使用气泡和语音提醒用户审阅总结。
- 只有用户明确说“确认上传”后才上传。
- 私有仓库名称为 `AngleBeatrowcolum/personal-weekly-summaries`。
- 仓库必须验证为私有后才能上传。
- 文件结构为 `summaries/<年份>/<ISO年份>-W<周数>.md`。
- 只提交指定的总结 Markdown，不使用 `git add .`。
- 上传失败时保留本地草稿，允许以后重试。
- 个人周总结不会自动发布到公开博客。

## 5. Astro 博客管理

### 5.1 已确认的博客信息

- 本地项目：`/home/user/myblog`
- 线上地址：`https://weblog.blind5883.top/`
- 博客技术：Astro 静态站点，Butterfly 风格主题
- Web 服务：Ubuntu Nginx
- 文章目录：`src/content/posts/<文章标识>/index.md`
- 当前博客不是 Typecho；页面中的 `Typecho-Butterfly` 只是主题来源名称。

### 5.2 第一版管理范围

Sakura 第一版支持：

- 创建 Markdown 文章草稿；
- 生成并检查文章 frontmatter；
- 查询和继续修改本地草稿；
- 在发布前展示标题、摘要和检查结果；
- 执行本地构建检查；
- 经用户明确确认后提交并推送指定文章；
- 查询自动部署结果；
- 用文字气泡和语音通知成功或失败。

第一版暂不支持：

- 未确认时自动公开文章；
- 删除或撤下线上文章；
- 批量修改历史文章；
- 管理评论、用户、主题或 Nginx 配置；
- 自动把私人周总结发布到博客。

### 5.3 发布确认门

保存 Markdown 和公开发布是两个独立动作：

```text
写入或修改 Markdown
        ↓
仅保存为本地草稿
        ↓
展示文章信息并等待用户检查
        ↓
用户明确说“确认发布”
        ↓
才允许提交和推送
```

写文章、保存文件、关闭 Sakura 或关闭 Codex/Claude Code，都不会自行触发公开发布。

## 6. GitHub/构建结果到 Nginx 的自动部署

这一段是博客发布闭环的必需部分，必须纳入博客管理实施计划。

目标流程：

```text
Sakura 保存本地草稿
        ↓
用户确认发布
        ↓
只提交本次文章相关文件并推送 main
        ↓
GitHub Actions 安装依赖并构建 Astro
        ↓
构建成功后，将 dist 安全部署到 Ubuntu Nginx
        ↓
检查线上首页和新文章地址
        ↓
Sakura 用气泡和语音报告结果
```

部署设计要求：

- 只有 `main` 分支上经过确认的提交可以触发生产部署。
- 构建失败时不得修改线上站点。
- 部署凭据使用 GitHub Actions Secrets，不写入仓库。
- 使用专用、低权限的服务器部署账号，不能获得不必要的系统权限。
- 校验服务器 SSH 主机指纹，避免连接到错误服务器。
- 先上传到临时发布目录，完成后再切换到线上目录，避免访客看到只上传了一半的网站。
- 部署失败时继续保留原线上版本，并记录可读的失败原因。
- 部署完成后至少检查：
  - 博客首页可以正常访问；
  - 新文章地址返回成功状态；
  - 页面中能够找到新文章标题。
- Sakura 不需要在整个构建过程中一直开启；再次运行或查询时可以读取部署结果。
- Git 历史作为文章版本记录，后续可以设计受控回滚，但第一版不允许 Sakura 自动回滚或删除。

实施前仍需确认：

- Nginx 当前实际站点目录；
- 服务器 SSH 地址和端口；
- 专用部署用户名及其最小目录权限；
- 使用 GitHub Actions 直接 SSH 部署，还是由服务器接收 Webhook 后拉取；
- 域名健康检查是否受 CDN、缓存或防火墙影响。

推荐优先评估“GitHub Actions 构建成功后，通过专用 SSH 部署账号上传构建产物”的方案；本地构建后直接上传和服务器 Webhook 拉取作为备选方案。

## 7. 建议实施顺序

1. 安装并验证 Sakura 当前版本需要的 Python 依赖。
2. 建立本地任务数据库、任务服务和 14 天清理机制。
3. 接入 Sakura 对话入口、今日任务查询、文字气泡和语音提醒。
4. 完成 Windows 开机自启动、计划任务、省电模式、QQ 邮件和错过提醒补偿。
5. 完成每周总结、本地草稿和私有仓库确认上传。
6. 完成 Astro 博客草稿创建、检查、预览和发布确认门。
7. 完成 GitHub Actions 构建到 Ubuntu Nginx 的安全自动部署。
8. 完成线上健康检查以及 Sakura 发布结果通知。
9. 根据实际需要再增加服务器提醒、实际交易日识别和高级博客管理。
